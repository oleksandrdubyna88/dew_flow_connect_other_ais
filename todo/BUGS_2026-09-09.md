**Asked for (no longer being built):** 35 % wider.

**Where.** `src_vs_code/src/panelView.ts:299-302` — the `What to ask about the selection`
textarea inside `chatBody`. It carries `rows="3"` and no width of its own, so it takes whatever
the section's field width is; every other control in the panel is the same width, which is why

## 2 — The prompt typed into the panel is not saved

**Symptom.** Type an instruction into *What to ask about the selection* (`поясни` in the
screenshot); it is gone again — the box comes back holding what it held before.

**What is already known from the code — no cause asserted yet.**

- The textarea posts through the shared `[data-setting]` listener, `panelView.ts:202-213`, on the
  **`change`** event. On a textarea that fires at BLUR, not per keystroke.
- The host writes it as a `plain` setting: `panelProvider.ts:918` → `settingsShape.ts:149`
  (`settingWrite`) → `panelProvider.ts:1053` (`save`), which is `config.update(… , Global)` inside
  a try/catch that surfaces a failure as an error toast.
- `coai.chatPrompt` IS declared, `src_vs_code/package.json:445`, so `config.update` has a
  registered key to write to.
- `chatPrompt` is **not** in `OVERLAID_SETTINGS` (`settingsShape.ts:222-226`), so the per-side
  overlay is not involved and the value goes to `settings.json`.

**First thing to test.** Whether a repaint replaces the webview HTML while the box still has
focus — the typed text would then die with the old DOM before `change` ever fires. The panel
re-renders on `onDidChangeConfiguration` and patches only two live regions
(`panelView.ts:216-232`); the textarea is in neither.

**The guarantee the red test should name.** Something like
`TextTypedIntoThePromptSurvivesARepaint` / `…IsWrittenToSettings`, not `chatPrompt bug`.

## 3 — The chat tab's composer scrolls away, and only Enter can send

Two things in one place, `src_vs_code/src/chatPage.ts:174-182` (`chatBody`).

**3a — pin the footer.** The textarea and the `Enter sends · Shift+Enter for a new line` hint are
the last two elements of a normal document flow, so they scroll with the conversation. They must
stay fixed at the bottom of the page and be unaffected by scrolling; the messages scroll behind

**3b — a Send button on the right.** Enter is the only way to send today. Add a button at the

button and the keybinding must go through the one `send()` in `chatScript`, never two paths.

## 6 — Markdown reaches the reader as raw text

**Symptom.** An answer arrives as markdown and is shown as markdown: `### Разбор деталей отчёта`
with its hashes, `1. **Проверка…**` with its asterisks, `` `merge-base` `` with its backticks,
`---` as three dashes. It must read the way the second screenshot reads — headings, numbered
lists, round bullets, indentation for nesting, code in a code face.

**Where.** `src_vs_code/src/chatPage.ts:87` — the body is `escapeHtml(message.text)` inside
`<div class="what">`, and `chatPage.ts:131` sets `white-space: pre-wrap`, which is the whole of
the current "rendering": the raw characters, wrapped.

**Reuse before writing a renderer.** `bodyHtml` in `src_vs_code/src/helpPage.ts:72` already does
this for the help page — paragraphs, `- ` bullets, `**bold**` — and its doc comment states the
safety rule the chat tab needs verbatim: **escape first, mark up second**, so nothing the text
contains can open a tag. Widening it (`###` headings, `1.` ordered lists, nested indentation,
`` ` `` code spans and fenced blocks, `---`) is the first move to try; a second renderer beside
it is the wrong answer.

**But the input is not the same kind of string, and this is the one thing not to get wrong.**
`bodyHtml` is fed the catalog THIS repository wrote. A chat answer is arbitrary text from another
vendor's model — untrusted, and this codebase has already shipped one autolinking/XSS defect of
exactly that family. Escape-first must survive every construct added; anything that emits an
attribute (a link `href`, an image `src`) needs its own scheme check, or is simply not supported.

**Two decisions.**

1. **Hand-widened `bodyHtml`, or a real parser?** The extension has **no runtime dependencies at
   all** today (`src_vs_code/package.json` declares only devDependencies), so `marked` +
   a sanitiser would be its first — bundled through esbuild, because the page's CSP is
   `default-src 'none'` (`chatPage.ts:287`) and nothing can be fetched. A real parser handles
   what a model actually emits; a hand-rolled one is another twenty lines that will be wrong
   about nested lists.
2. **Where does it run?** Rendering in the extension host and posting HTML keeps the webview
   script small; rendering in the webview keeps the untrusted text out of the host. Either is
   defensible — pick one and say which.

**This decides entry 5's open question 2.** A line of 56 asterisks IS a markdown thematic break,
so once markdown renders, the asterisk row becomes an `<hr>` on its own. Build entry 6 first,
then see whether entry 5 still needs anything.

## 7 — Links, blue and clickable

**Asked for.** The reference screenshot is Claude Code's own rendering of the same answer: the
file references are blue links you can click. Ours should have them too, in the same blue, where
it is possible at all.

**Not a separate feature — the second half of entry 6.** Those blue links are markdown links,
`[panelView.ts:203](src_vs_code/src/panelView.ts#L203)`, and today they arrive as their raw
bracket-and-paren source. A renderer that emits `<a>` is the same change.

**The blue is the theme's, not a hex value.** `var(--vscode-textLink-foreground)` with
`--vscode-textLink-activeForeground` on hover — already what this repo colours a link with:
`panelView.ts:1363-1366` and `roundsLog.ts:781`. A hardcoded blue would be wrong in half the
themes.

**This is the construct entry 6 warns about — the first one that emits an attribute.**
`href` is where escape-first stops being enough, and this codebase has already shipped an
autolinking defect. Rules the fix has to hold:

- **Allow-list the scheme.** `https:` and `http:` only, plus whatever internal form the file
  links take. `javascript:`, `data:`, `vbscript:` — and anything unrecognised — render as plain
  text, never as an anchor.
- **Only what markdown SAID is a link.** Do not autolink bare URLs found in the model's prose;
  that is precisely the defect already fixed once elsewhere in the family.
- **A file path is not a URL.** The chat webview is created with `localResourceRoots: []`
  (`chatPanel.ts:99`), so it can load nothing from disk; opening `src/foo.ts#L203` in the editor
  has to go back to the host as a `postMessage` — the same bridge the page already uses for
  `send` and `pageError` — which then does `vscode.window.showTextDocument` at that line. Command
  URIs are not enabled and should stay that way.
- **External links leave the webview.** `http(s)` anchors are handed to
  `vscode.env.openExternal` (`panelProvider.ts:856` is the existing precedent), never navigated
  in place.

**Open question.** Whether a file link should resolve relative to the repository the chat was
opened FROM. The tab is named after a session, and an answer can name a path in a repository the
person is not in; a link that opens the wrong file with a confident line number is worse than
plain text. Default: resolve against the workspace folder, and leave anything that does not
resolve as plain text rather than a dead blue link.

## 8 — The text is dim and small

**Asked for.** Brighter and bigger — the way Gemini's app reads: high-contrast body text, a
comfortable size, room between the lines.

**Where, and what is actually making it dim.** All of it is `chatStyle`,
`src_vs_code/src/chatPage.ts:122-145`.

- `body` takes `var(--vscode-foreground)` (`chatPage.ts:125`). That is the CHROME's foreground —
  the colour of a label on a button. Editor prose uses `var(--vscode-editor-foreground)`, which
  is the brighter of the two in the dark themes and is what a wall of text should be read in.
- Three separate rules then dim it further with opacity: `.msg.you .what { opacity: .85 }`
  (`chatPage.ts:132`), `.passage { opacity: .85 }` (`:128`), `.msg .who { opacity: .7 }` (`:130`).
  The message bodies must lose theirs outright — entry 4 gives `.msg.you` a real colour, and
  a colour plus an opacity is two people deciding one thing.
- `font-size: var(--vscode-font-size)` is the editor's UI size (13px), not a reading size.
- There is no `line-height` and no column width at all: full-width lines at 13px with default
  leading is the shape being complained about.

**The zoom already exists — do not add a second one.** `coai.uiScale` is a real synced setting
with ± buttons in the header (`zoomControl.ts`, used at `chatPage.ts:174` and by the help page,
`helpPage.ts:174-178`). This entry is about the DEFAULT being wrong, not about giving the person
a knob they already have. Change what the page looks like at scale 0.

**Open question.** A reading column (Gemini's app caps the measure — the screenshot's text does
not span the window) or full width? A cap reads better and fights entry 4's right-aligned `You`
less; full width uses the tab somebody deliberately made wide. Default: cap the prose, let code
blocks scroll inside their own box.

## 9 — Two scrollbars

**Symptom.** There are two scrollbars at the top of the tab: the page's own, and a small inner
one belonging to the box that holds the captured passage. Scrolling up should just be scrolling
up, the way it is in Claude or Gemini — one scroll, the whole conversation.

**Where.** `src_vs_code/src/chatPage.ts:128` — `.passage { … max-height: 180px; overflow-y:
auto; }`. That is the inner bar, and the outer one is the document.

**Why it was written that way, and why the reason is about to expire.** The rationale is in the
file's own header, `chatPage.ts:19-24`: the passage is shown so a person sees a STALE clipboard
before the answer does — the gate raised that three times, so the block itself stays — and it was
capped because *"a fifty-line selection would otherwise push the composer off the screen on
open."* **Entry 3 pins the composer.** Once the composer cannot be pushed anywhere, the cap has
nothing left to protect, and the passage can scroll with the page like everything else.

**So 3 and 9 are one change, in this order:** pin the composer, then remove the cap and the inner
`overflow-y`. Removing the cap first reintroduces exactly the defect the comment records.

**Keep the passage distinguishable.** Losing the scrollbar must not lose the left border and the
spacing that say "this is the text being discussed, not the first thing anybody said". A very
long selection now pushes the conversation down instead of the composer away — acceptable,
because the conversation is what you scroll to, and it is where the page should land on open.

## 10 — The menu path opens the console instead of a tab

**Symptom.** Copy, then right-click: what happens is the Output console, not a chat tab. The
keybinding on the same selection opens the tab. **Both paths must open the tab.**

**What the screenshot's own log already proves.** The `COAI probe` channel shows the capture
SUCCEEDING: `path : MENU (read the clipboard as-is)`, `RESULT : took 1322 chars from the
clipboard in 3 ms`, and a `captured :` line holding the right text. So this is not a capture
failure — whatever should have followed a good capture did not open a tab.

**The first thing to establish, before anything is diagnosed.** The context menu in the
screenshot holds TWO items that both grab a selection:

- `Chat with other AI` — `Ctrl+Alt+A`. This one is ours: `package.json` declares exactly one
  `webview/context` entry, `coai.chatWithOtherAi`, `when: webviewId == 'claudeVSCodePanel'`.
- `COAI probe: grab the selection` — `Ctrl+Shift+Alt+G`. **This command does not exist anywhere
  in this repository** — not in `package.json`, not in `src_vs_code/src`. It is a separate probe
  extension installed alongside, and `COAI probe` is ITS output channel. Writing to an output
  channel is what a probe is for.

So the question to answer first is which of the two was pressed. If it was the probe's, there is
no defect in this product and the fix is that the probe is uninstalled or renamed so the two
cannot be confused. If it was `Chat with other AI`, this is a real defect in the menu path and
the probe's log is a coincidence sitting in the same screenshot.

**Where the menu path lives if it is ours.** `src_vs_code/src/chatCommand.ts` — the trigger
distinction is `fromMenu`, the same flag `sendsImmediately` reads (`chatSettings.ts:88-96`). The
menu path reads the clipboard as-is; the keybinding captures the selection itself. Note that with
`chatAutoSend` at its default `keyboard`, the menu path is DESIGNED not to send — it fills the
composer and waits. **That is not this bug.** "Fills a tab and waits" is still a tab; the report
is that no tab appears at all.

## 11 — The composer does not grow with what is typed

**Asked for.** The box being typed into grows with the text up to **30 % of the screen height**,
and only then starts scrolling. (`Never — always let me press Enter` is the chosen send mode, so
a long multi-line question is now the normal case, not an edge one.)

**Where.** `src_vs_code/src/chatPage.ts:141` — `textarea { … min-height: 64px … }`, with
`rows="3"` on the element itself (`chatPage.ts:181`). There is a floor and no ceiling and no
growth: the box is one fixed size and the text scrolls inside it from the fourth line on.

**Try the CSS first.** `field-sizing: content` with `max-height: 30vh` does the whole thing with
no script — the box sizes itself to its content and stops at the cap. It is Chromium-only, which
here is not a limitation: the page only ever renders in VS Code's own webview. The extension
declares `engines.vscode ^1.85.0` (`package.json`), and old enough hosts would simply keep
today's fixed box rather than break — so the fallback is the current behaviour, which is
acceptable. If it does not hold up, the script fallback is the usual one: on `input`, reset
`height` to `auto`, then set it to `min(scrollHeight, 30vh)`.

**It has to be built together with entry 3.** A composer pinned to the bottom whose height
changes is a footer whose height changes: the conversation's scroll area has to give back the
space the composer takes, or a growing box will cover the last message — the exact complaint
entry 3 exists to fix, reintroduced from the other direction. Whatever holds the messages must
be laid out against the footer's real height (a flex column, or the footer's height read into a
custom property), not against a constant.

**Two details not to lose.** The 30 % is of the VIEWPORT, not of the conversation — `30vh` in a
webview is the tab's own height, which is what "screen" means here. And the box must SHRINK
again when the text is deleted or sent, not stay at its high-water mark.

## 12 — A library of named prompts, not one box

**This is a feature, not a defect** — the largest item in this file, and the one that will
probably leave it as its own `todo/PLAN_*.md`. Recorded here so nothing is lost.

**What was asked for, in the operator's own order.**

1. **Several prompts, saved.** Today there is exactly one: `coai.chatPrompt`, a single string.
2. **A tick marking which one is the MAIN one** — the one used by default *when the trigger sends

3. **Every prompt has a NAME**, and each is a **button above the composer**, on the row where the

4. **CRUD in a tab of its own**, not in the sidebar: the list of what exists, edit of BOTH the

**What already exists, and what it does and does not give.**

- **The reviewer prompt catalog** — `src_vs_code/src/prompts.ts` — is already a list of
  `{ id, label, purpose }` chosen from a panel section (*Prompts per round*), written by
  `choosePrompt` (`panelProvider.ts:887`) into `promptsPerRound`. Its SHAPE is the shape asked
  for here, and the naming should follow it. What it is not: it is a catalog this product ships
  and a person overrides, not a list a person creates and deletes. So this is a sibling of it,
  not an extension of it.
- **A tab of its own is a solved pattern, twice over**: the rounds log (`roundsLog.ts` +
  `roundsLogPanel.ts`) and the help page (`helpPage.ts` + `helpPanel.ts`) are each a page module

- **The button row already exists**: `chatPickerHtml` (`chatPage.ts:93-107`) renders the model
  picker and its caption into `.picker` (`chatPage.ts:139`). The prompt buttons belong on that

**Storage, and the one thing that must not be got wrong.** A list plus a default is two new
settings (`coai.chatPrompts` as `{id, title, text}[]`, `coai.chatPromptDefault` as an id) beside
the existing four. **The single `coai.chatPrompt` a person has already typed becomes the first
entry, carrying the default tick** — never dropped, and never silently left behind as a fifth
setting nothing reads. Keep the chat settings' existing two decisions: NOT in `OVERLAID_SETTINGS`
(`settingsShape.ts:222`), and NOT mirrored to the server — `chatSettings.ts:11-16` says why, and a
prompt library is exactly the kind of thing that would otherwise start travelling.

**Open questions.**

- **Does this retire entry 1?** That entry widens the sidebar box by 35 %. If prompts are edited
  in a big box in their own tab, the sidebar's role shrinks to *picking* one — and a picker does
  not need 35 % more width. Ask before building both.
- **What happens to the sidebar box?** It becomes a picker (a dropdown of names, plus an *Edit…*
  that opens the tab), or it stays an editable box for the selected prompt. The first is
  simpler and matches "the CRUD is in the tab".
- **A prompt per model, or one library?** Not asked for; do not build it. Noted only so the data
  shape does not make it impossible later.

## 13 — Pasting an image into the composer

**Asked for.** Paste a picture from the clipboard into the composer, the way Claude Code and
Gemini take one. **A feature, not a defect** — and the one item in this file whose cost is not
in the page at all.

**Three separate problems, and only the first is layout.**

**a — Taking the paste.** The webview can have it: a `paste` listener on the textarea reads
`event.clipboardData.items`, and an `image/*` item gives a `Blob`. That part is ordinary. It goes
to the host over the bridge the page already has (`postMessage`, as `send` and `pageError` do),
because the webview can write nothing to disk itself.

**b — Showing it.** The page's CSP is `default-src 'none'` (`chatPage.ts:287`) — which blocks
images too — and the panel is created with `localResourceRoots: []` (`chatPanel.ts:99`), so it
can load nothing from the filesystem either. A thumbnail in the composer and the image in the
conversation both need `img-src data:` added to that CSP, and nothing wider: `data:` for images
only, no remote host, no `file:`.

**c — Delivering it to a model, which is the part that decides whether any of this is worth
building.** `ChatSession.send` takes `text: string` and nothing else (`chatSession.ts:37`), and
under it are four implementations — `claudeAdapter`, `codexAdapter`, `agyAdapter` and
`remoteChatSession`. **Whether each vendor CLI accepts an image at all, and how (a file path in
the prompt, a flag, base64 on stdin), is not known and must be MEASURED before the seam is
widened** — the three-adapter plan's own record says a written-down assumption about these CLIs
was already half wrong once, and measurement is what corrected it. Establish per vendor:

1. Does the CLI take an image in a non-interactive turn?
2. By what mechanism, and does it survive `cmd.exe` on Windows?
3. What does the Team server do — `remoteChatSession` sends a job over the wire, so an image is
   a wire-format change on a server that ships separately from this extension and is deployed by
   hand. Expect the client to be able to send one long before a server can take one.

**What must NOT happen: a picture that silently does not arrive.** If the chosen model cannot
take images, the paste is refused in the page with a sentence naming the model — the same rule
the model picker already follows by naming the models that cannot answer a chat
(`strandedOption`, `panelView.ts:274`). Dropping it quietly is the worst of the three outcomes.

**Housekeeping.** A pasted image becomes a temp file the CLI reads. It has an owner and a
lifetime, like the vendor processes do — `chatOrphans.ts` is the existing precedent for "a
force-killed VS Code leaves nothing behind"; images belong in the same discipline, not in
`%TEMP%` forever.

## 20 — The chat tab has no icon

**Asked for.** A bright **green** icon on the tab, from our palette, using the glyph the operator
supplied — and **big**, the way VS Code's own Welcome tab icon is.

**Where.** `src_vs_code/src/chatPanel.ts:95-100` creates the panel and never sets `iconPath`.
`grep` finds **no `iconPath` anywhere in `src_vs_code/src`**, which is why the tab wears the
generic `≡` every webview gets by default.

**The pieces already exist.**

- `media/` already ships SVGs and is not excluded by `.vscodeignore`, so a new file is packaged
  with no build change: `panel.svg` (the activity bar) and — the exact precedent needed here —
  `help-yellow.svg` **and** `help-yellow-light.svg`, a themed pair.
- The green is `#5CC46F`, palette slot 5 (`vendorColour.ts:63`). Take it from there rather than
  eyeballing one; it is the green `gemini` already wears, and the palette's own comment says the
  twelve were chosen to stay apart in a light theme as well as a dark one.

**Two constraints that decide how this is built.**

1. **A tab icon cannot read the theme.** It is workbench chrome, not webview content, so

2. **"Big" is not a size you can ask for.** The workbench draws a tab icon at its own fixed size;

   declared done from the file.

**The glyph was ours all along** — the operator pointed out on 2026-09-09 that it is
`media/panel.svg`, the activity-bar icon. The recoloured pair (`chat.svg` #5CC46F, `chat-light.svg`
#2E8B3E, full-bleed, thicker strokes) is in `media/`; the plan holds the numbers.

## 21 — Pick the provider first, then the model

**Asked for.** Two steps instead of one: choose the provider (codex, claude, google), then the
model. A **Team server** can be chosen as a provider too — and there only what that server allows
is offered.

**What the picker actually is today, which is the root of the complaint.** It is not a list of
models at all. `chatModelsFrom` (`src_vs_code/src/chatModels.ts:111-129`) maps each **configured
vendor row** to one entry, labelled `${vendor.id} · ${vendor.model}` — so `gemini ·
gemini-3.8-flash-low` is one reviewer row, and the model in it is whatever that row is set to.
There is no way to pick a different model without going to the panel and re-configuring the
reviewer, which is why the list reads as an arbitrary handful.

**Everything the two-step picker needs already exists — this is assembly, not invention.**

- `modelsFor(runtime, discoveredCodex, current, localEngine, discoveredAgy, allowedRemote)`
  (`src_vs_code/src/models.ts:94`) is exactly "the models of ONE provider": discovered for a local
  engine and for codex/agy, curated for Claude (`CURATED_CLAUDE_MODELS`, `models.ts:88`), and — for
  a Team server — the server's own allowlist, with a saved-but-withdrawn model kept and MARKED
  rather than dropped (`models.ts:105-112`). That marking rule is the operator's "только то, что
  разрешено", already built.
- `allowedModelsFor(vendor, teamServers)` (used at `panelView.ts:407`) is where a server's allowed
  list comes from.
- The reviewer card in the panel is ALREADY a provider → model pair of controls
  (`vendorCard`, `panelView.ts:598-635`). The chat picker is the odd one out; make it look like
  the thing that already works.

**The one real decision, and it is not cosmetic.** Does the chat still pick a CONFIGURED ROW, or
does it get its own provider+model independent of the reviewer rows?

- Picking a row is what everything downstream assumes today: the row carries the runtime, the
  executable, the base URL, the price, and for a Team server the server AND `remoteVendor`. The
  boundary check exists on that basis — the panel "refuses a `pick` naming a model the
  conversation was not offered" (`chatModels.ts:8-11`).
- Choosing provider+model freely is what was actually asked for, and it means the chat needs its
  own small config: which provider, which model, and for a remote one which server. It also means
  a model can be picked that no reviewer row uses — which is fine for a chat, and is probably the
  point.

Recommendation: provider+model of its own, resolved to a runtime/executable through the same
vendor rows, with the row supplying HOW to run it and the picker supplying WHICH model. Ask
before building — it changes `chosenModel`, the offered/refused boundary, and what the ledger
records as having answered.

### 21b — Named model presets, as buttons, exactly like the prompts

**Added by the operator after the two-step picker was recorded.** The same shape as entry 12: a
place to add several MODELS, give each a name, and give each a **starting prompt** — and they
appear as buttons above the composer too.

**DECIDED 2026-09-09: TWO ROWS, not one merged list.** The proposal to fold prompts and models
into a single `{name, provider, model, startingPrompt}` preset was put to the operator and
**refused**: one row of MODEL sets and one row of PROMPT sets, above the composer. They stay two
kinds of thing because they are two kinds of decision — *what shall answer* and *what shall be
asked* — and one button that silently sets both is a button whose effect you cannot predict from
its name. They still share one CRUD tab with the big readable editor entry 12 asked for; two
sections in it, not two tabs.

**The colours: one for the model row, another for the prompt row, both unobtrusive but legible.**
That is the operator's instruction, and there is one conflict in it worth naming before it is
built.

- **A flat single colour for every model button collides with a rule this product already
  holds** — one vendor, one colour, everywhere (`vendorColour.ts`; the rounds list and the
  reviewer cards already obey it, and entries 4, 17 and 20 extend it to the chat). A green model
  button that is not `gemini` teaches the opposite of what every other surface teaches.
- **Recommended instead:** each MODEL button wears its own vendor's colour from `vendorPalette` —
  which is still "the model row is coloured" to the eye, and stays consistent with the rest of the
  product — while the PROMPT row takes one neutral, non-palette accent so a prompt can never be
  mistaken for a vendor.
- **Unobtrusive means an EDGE, not a filled box.** That decision was already made and shipped once
  in this repository, for the reviewer cards, with its reason recorded
  (`research/PLAN_reviewer_card_colours.md`). Follow it rather than re-deciding it.

**DECIDED 2026-09-09 — the operator delegated the choice** (*"выбери сам, потом изменим если
что"*), so the recommendation stands: model buttons wear their own vendor's colour as an EDGE;
the prompt row wears one neutral, non-palette accent. Recorded in the presets plan; changeable
later by design, since it is an edge colour and not a data shape.

**Two traps this must not walk into.**

1. **`remoteVendor` is the field this family has already lost once.** Every component written
   before it existed dropped it, silently, for three releases
   (`research/PLAN_team_server_reviewer_never_called.md`). A two-step picker that selects a Team
   server must carry the server AND the vendor name on that server, or it reproduces exactly that
   failure — a 400 saying `'<server>-<vendor>' is not a vendor here`, in seconds, for no tokens.
2. **A model must not reach the wrong adapter.** `vendor-routing.md` is explicit that a Claude
   model never goes through `agy`; the adapter map chooses the adapter and the executable together
   (`chatModels.ts:15-21`). A free provider/model choice makes it newly possible to ask for a
   combination that has no adapter — refuse it BY NAME, the way `refused` rows already are.

## 15 — A turn cannot be stopped once it has started

## 16 — The conversation does not survive a window reload

> **ACCEPTED 2026-09-09, but explicitly LOW PRIORITY** — *"не критично; если это легко — делай"*. So:

## 22 — What a conversation costs is shown nowhere

> **ACCEPTED 2026-09-09**, and widened by the operator: *"плюс в логах отдельно"* — in the tab
> AND as its own line in the rounds log, not only in the tab.

**Why it matters more here than in a review.** A chat turn carries the whole conversation so far,
so question five is billed for questions one through four as well. The code says this out loud —
`chatCommand.ts:503`, *"the next question costs more than the last one, because it carries
everything said so far"* — and it is the one number a person would use to decide whether to ask
again, or to start a fresh conversation instead. It is currently invisible at the exact moment
the decision is made.

**Two places, two different numbers.**

1. **In the tab** — what THIS conversation has cost so far, updated as it goes. Live, next to the
   model picker, where the decision to ask again is taken.
2. **In the rounds log** — chats as their own rows, priced like rounds are, so a month of chatting
   can be seen beside a month of reviewing. The Team server already made this separation on its
   side (`research/PLAN_the_server_knows_a_chat_from_a_review.md` — a chat is `kind: chat`, and its
   spending page separates conversations from rounds); the local log has not caught up.

**Where the numbers come from, and the one honest limitation.** The usage ledger and the price
tables already exist — `modelPrice` (`panelProvider.ts`) prices a model from the two public lists
plus whatever the operator typed per vendor, and the log's Cost column is built on it. The
limitation is recorded in the family's memory and in `todo/PLAN_usage_that_compares.md`: the three
vendors do not report comparable token counts (claude counts cache reads, antigravity omits cache
entirely, codex reports a cumulative maximum). So a chat's cost is an ESTIMATE for at least two of
the three, and it must be marked as one — the tilde convention `usage.ts:230` already uses:
`~$0.42` is what the tokens work out to, `$0.42` is what a vendor actually charged.

## 23 — Three entries move the scroll, and where the page looks was never decided

**Not a defect — a decision that has to be made once**, before entries 3, 9 and 11 are built.
Each of them changes what scrolls: 3 pins the composer and so gives the messages their own
region, 9 removes the passage's inner scrollbar, 11 makes the composer's height change under it.
Three separate implementations will each answer the following three questions their own way, and
the result is a page that behaves differently depending on which of them you provoked.

**DECIDED by the operator, 2026-09-09 — all three as proposed. This is the rule entries 3, 9
and 11 implement; none of them decides any of it again.**

1. **On open, the tab looks at the LAST message.** The captured passage stays above it and is
   reached by scrolling up. Today the passage is at the top and pinned by its own scrollbar, so
   this is a real change and entry 9 is what makes it possible.
2. **A new answer scrolls the page to itself ONLY if the reader was already at the bottom.**
   Somebody who has scrolled up to read is never yanked away mid-sentence.
3. **A reader who is scrolled up gets a *jump to the newest* control**, the way Claude does it —
   so the answer that landed out of view is not silent.

**What "already at the bottom" has to mean in code, or rule 2 will feel broken.** Not
`scrollTop + clientHeight === scrollHeight` to the pixel: a threshold (a line or two of slack),
because a page that is one pixel short of the bottom is a page the reader considers to be at the
bottom. And the check is taken BEFORE the new content is inserted — measuring after it has been
added always says "not at the bottom", which would silently turn rule 2 into "never follow".

**Two consequences for the entries that move the scroll.**

- **Entry 11** changes the composer's height while an answer may be arriving. When the composer
  grows, a reader who was at the bottom must STAY at the bottom — otherwise typing a long
  question scrolls the last answer out of view, which is rule 2 broken from the other side.
- **Entry 15** (a stopped turn) and a failed turn end the same way: whatever is rendered in place
  of the answer follows the same rule as an answer. There is one rule, not one per outcome.


## 24 — Empty Enter after a model switch: ask the OTHER model the same thing

**Asked for.** *"Maybe I don't like gemini's answer and want to switch to Fable or Astra. If I
switch the model and press Enter with an empty box — take the previous context (except the last
answer) and feed it to the new model."*

**This is a re-ask, and the machinery for it is already built and shipped.** Switching the model
mid-conversation already carries the whole thread across:
`carriedTurn(said, question, language, budget, fenceId)` (`src_vs_code/src/chatPrompt.ts:172`)
takes a transcript AND the question to put at the end, and `chatCommand.ts:225-226` already
chooses the budget and calls it. What this asks for is one specific pair of arguments to that same
function:

- **`said`** = the conversation **minus the last model answer** — that is the operator's
  "кроме последнего ответа", and the reason is sound: an answer you rejected, handed to the next
  model, is a model being asked to agree with it.
- **`question`** = the last thing YOU said, re-used verbatim. It is not re-typed and it is not
  lost — `carriedTurn` already puts the question last on purpose, because recency belongs to the
  question rather than to the transcript (`chatPrompt.ts:165-170`).

So this is a small, well-supported change, not a new mechanism.

**The gesture is currently inert, which makes it safe to take and easy to hide.** `send()` refuses
an empty box today — `if (text.length === 0) { return; }` (`chatPage.ts:204`) — so nothing is
being overloaded. But a feature whose only trigger is "press Enter on an empty box" is a feature
nobody discovers. **It needs a visible affordance**: with entry 3b's Send button already on the
composer, the button reads *Re-ask · <new model>* whenever the box is empty and the model has
changed since the last answer. One gesture, two ways in.

**Four decisions.**

1. **Does the rejected answer stay on screen?** Recommended: **yes**, kept and labelled with the
   model that gave it (entry 17). Two answers to one question from two vendors, side by side, is
   this product's whole subject — deleting the first one throws away the comparison the operator
   is making. It is only excluded from what is SENT.
2. **What if the model was not switched?** Then empty Enter is a plain "ask the same model again",
   which is a different feature (regenerate) and was not asked for. Recommended: do nothing, as
   today, and let the Send button stay disabled — an accidental Enter must not spend a turn.
3. **A Team server costs a turn from a budget of three** (`REMOTE_TURNS`, and
   `REMOTE_CARRY_BUDGET` is a third of the local one, `chatPrompt.ts:97-108`). A re-ask against a
   remote model spends one of those three and re-sends the transcript. Say so before it is spent,
   the way the picker's caption already says a Team server keeps no memory.
4. **What if the last thing in the conversation is YOUR question** (the previous answer failed, or
   was stopped by entry 15)? Then there is no last answer to drop and the re-ask is simply the
   same question to a new model. Handle it; do not let it produce an empty `question`.
